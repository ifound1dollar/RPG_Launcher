# RPG_Launcher

This WPF application acts as a basic launcher for an in-development multiplayer RPG. It is designed to securely connect via HTTP w/TLS to a running login API service and allow users to perform typical login-related operations. It will eventually be used by players to log into and launch the game.

---

## High-level Description

On launch, the application calls the login API to try to log in using a stored refresh token, if one exists. This refresh token is supplied by the server (API) on successful login and is securely stored client-side for future logins and access token refreshes without requiring the user to re-enter their username and password. If this initial attempt is unsuccessful for any reason (nonexistent refresh token, expired token, etc.), the application shows the login screen and auto-populates the 'username' field with the username of the account which most recently logged in using this application. The user must then log in using their username and password. On successful login (whether manually or via the initial refresh login attempt), the application displays the main window. The main window includes an account settings/information screen which displays account information and allows changing username and password, and allows logout.

Application logic follows the model-view-viewmodel pattern for all logic, isolating all UI operations into views, data into models, and using viewmodels as the communication pipeline between the two. The MainViewModel class is a singleton that acts as a centralized point to switch between different views during application execution. It includes methods to switch views, but does not implement any logic itself (the sub-ViewModels it manages handle logic internally). These sub-ViewModels are responsible for binding data between the model logic and the view(s); the built in 'code-behind' files are only responsible for UI-relevant actions like window minimization and closing. However, the SecureString data type used by the password input field does not support typical MVVM binding, so the MVVM pattern is deviated from slightly for security reasons. Instead of directly binding the password input field to the Password property in MainViewModel, the relevant _View.xaml.cs code-behind files directly assign the ViewModel's SecureString property using the stored value. This is necessary in order to allow the SecurePassword field to be cleared and nullified immediately once the password is consumed (binding does not allow this, creating a security risk). Likewise, the login button press also manually calls the login button command within the viewmodel in order to enable the password input field to be cleared immediately on login. Generally, this is an acceptable deviation from the 'pure' MVVM pattern.

An API service singleton class called LoginApiService is used to facilitate communication between the application and a remove login service API. Only one API service is needed at any time during the application's lifetime, which is why the static singleton pattern has been used for this service. Currently this service utilizes a temporary login API imitator called TempLoginApiImitator rather than actually communicating with an API; this is ultimately to make testing and development easier. The temporary API imitator stores data locally and exists exclusively for testing (data stored is not secure). In the future, the LoginApiService will run an HttpClient that communicates securely with the API and awaits a response. The login service API will perform CRUD operations on the local database, which at the moment is using MongoDB.

Local application data is stored in a file called appdata.json and is accessed immediately on application startup. This file stores basic data like version, initial run timestamp, client GUID to identify unique client machines, and the last-logged-in account's username (used to automatically populate the username field, which was mentioned above). The AppData class stores the data retrieved from the file in a handful of local fields, and automatically updates some fields that may change while the application is running (ex. saved username on login success). Additionally, the class stores two JWT tokens in memory: a refresh token used to log in without requiring the user to enter their username and password each time, and an access token which is required to actually access any API endpoint other than login endpoints. On a high level, a refresh token denotes that a user has accessed their account but is not fully logged into the API, while an access token denotes that the user is fully logged in and can access the API (access tokens include various Role claims which control which endpoints the user can access). The access token is short-lived and is thus only ever stored in memory, but the refresh token is long-lived and must be securely stored on the disk. This is discussed in more detail below, but the high-level description is that the DataProtection class manages reading and writing data to a secure file with the help of the Windows Data Protection API (DPAPI). The AppData class utilizes DataProtection to read the refresh token on startup, and securely write the token to disk any time it changes (for example, a new refresh token is received on any successful login or any time that a new access token is received). See the below section for more details on client- and server-side security.

## Application and API Security

This application is responsible for and accesses sensitive user data like username, password, and secure tokens, and thus security is incredibly important. First and foremost, all communication between the client and the server is done over HTTPS. Additionally, secure JWT Tokens are used for various authentication operations and are carefully managed both client- and server-side. Short-term access tokens are used for actual API actions, while longer-term refresh tokens are used by clients to login without requiring username and password each time. These tokens are carefully handled to minimize the possibility of a security breach, and various actions are taken to invalidate tokens if any suspicious activity is detected (this is done primarily server-side). The below sections discuss security considerations for both sides of the equation.

### Client-side

Sensitive data like passwords and login tokens are never stored in plain text outside of memory on the client. As soon as the user enters their password and makes a login or register request to the API, the memory that held the password is cleared along with any input fields. Access and refresh tokens that are received upon login are stored in memory, though the refresh token is encrypted and stored in a secure file on the disk (more on this below). Clients also store various data in a file named appinfo.json which resides in the executable's working directory; data here includes application version, timestamp from when the application was first launched, a GUID that is generated on first launch to identify unique client machines, and a string holding the last-logged-in username so the username field can be auto-populated when the user needs to log in again. Every time the application is launched, this data is verified and updated if necessary (ex. if the application version changes); the saved username is also updated any time that the client logs into a different account. Importantly, this data is *not* considered highly sensitive and is thus not stored securely because it exists primarily to identify user-specific application data.

One of the pieces of data that *must* be stored securely is the longer-term refresh token that the client receives upon successful login. Any time that a new login request is successful, the client receives a new token and replaces the old token if one exists (renewing the refresh token on each login is typical). In order to remain logged in across separate application launches (ex. the next day after the computer was shutdown), this refresh token must be stored on the disk somewhere. This is done using the DataProtection class, which uses a handful of methods including the Windows Data Protection API (DPAPI) to encrypt and decrypt the credentials file which contains the refresh token. By design, the encryption is application-specific and Windows user-specific. The methods in which this encryption and decryption is performed are not discussed in detail here, but it can be seen in the DataProtection class.

### Server-side

Again, sensitive data like passwords and tokens are never stored in plain text outside of memory. Similar to the client application, passwords sent to the server on login request are immediately removed from memory as soon as they are processed, and only secure password hashes that are hashed using current OWASP standards are stored in the database. Refresh tokens are also stored in the database alongside each user's account information, and they are also hashed using a similar scheme. Access tokens are only stored in memory and will never appear on the disk.

Login API requests are carefully validated to ensure that they are not malicious. The first operation that the client application will make is to try and login via a securely-stored refresh token (if the client user is already logged in). To ensure that the token is valid, the server queries the database to determine whether the sent token matches the token stored in the database. Additionally, the server also requires that clients send an application-user-specific GUID with each login request (all login types, refresh or regular). This can be helpful to determining if an entirely different machine is making the login request, which can be useful for detecting and handling malicious activity (see next paragraph). This does require the user to re-login whenever they update their application version, but this only a mild inconvenience and represents a very uncommon scenario.

- Importantly, one must consider that it is quite easy for a malicious client application to spoof its GUID and pretend to be the valid client. For this reason, the GUID will be most often used to determine the source of each login request for account security reasons. For example, if the same account has received numerous login requests from applications with different GUIDs over a short period of time, it is safe to assume that the account is being attacked and perhaps the account should be locked until the password is changed. A login attempt tracking system will be implemented server-side in the future for this scenario specifically.
